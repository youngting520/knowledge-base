## 把 AI 工作拆成三层：提示词、上下文与 Harness 运行流程

<a name="work-7707287096683154738"></a>

**学习场景**　手头有一个反复跑偏的 AI 任务，想找出应该改指令、补资料，还是改执行流程。

- 准备一项低风险练习，例如给两个人拟一份周末行程。前三章解决怎样说清任务、选对资料，后几章处理工具调用、验证和人工确认。

### 00:00:00　先定位问题属于哪一层

- 片中先区分承载模型的计算环境、对外提供调用的接口，以及供人交互的聊天界面。能在聊天框给出计划，并不自动表示它能执行计划中的动作。
- 给任务写下三个问题：我有没有说清结果，模型能看到必需的信息吗，这套系统有工具执行并回报结果吗？

**练习**　用一个行程草案举例，把「整理成表」「知道出发地」「能查班次」分别写入三栏。

**自查**　缺少每一项时，你都能说出相应的修复动作。

<a name="work-7707287096683154738-chapter-2"></a>

### 00:01:20　写提示词时交代约束与可验证的输出

- 原片的排序例中，只说「加个排序」，模型可能只返回排序片段。把排序字段、方向、需要完整函数、原有行为要保留等要求写清，再给一条可检验的输入。
- 规则过多或互相冲突时，先写出本次最重要的要求，再删除重复表述。若要它写代码，给一个能检验输出的输入样例。

**练习**　把「帮我排行程」改成「按出发时间列出三项，表中标出地点和交通时间；缺资料填待查」。给它一条故意缺时刻的输入。

**自查**　成品列名正确，缺失值能被发现；修订效果能用同一份输入对照。

[返回章节目录](#work-7707287096683154738-chapters)

<a name="work-7707287096683154738-chapter-3"></a>

### 00:02:15　准备上下文：选材料、裁剪、安排顺序

- 原片把上下文拆成指令、资料、状态。规则和任务属于指令，聊天与参考文档提供材料，工具回报和记忆交代事情走到了哪一步。
- 先召回与本次决定相关的内容，再裁掉无关段落，最后安排位置。稳定规则放前面，临近执行时让关键限制再次可见。

**练习**　拿一段长聊天，选出与目标、时间和预算直接相关的三句话。给模型看精简材料，再看它会不会引用无关的旧计划。

**自查**　每段材料都能回答「拿掉它会影响哪个决定」。冲突的两种说法有标记，不会被默默揉成一条。

[返回章节目录](#work-7707287096683154738-chapters)

<a name="work-7707287096683154738-chapter-4"></a>

### 00:04:20　搭起模型、工具与反馈之间的执行循环

- 运行框架先组织上下文，让模型决定下一步，由外部程序实际执行，再把真实结果带入下一轮。区分「准备去查」与「已收到结果」。
- 经常复用的项目目标、技术栈、风格和限制可整理成规则文件，使后续执行有一致的起点。

**练习**　在纸上走一轮：提出查班次的需要，返回一条示例班次，再让规划步骤利用这个结果更新行程。

**自查**　删去工具返回值，报告就应显示待查；不能把拟议动作标成已完成。

[返回章节目录](#work-7707287096683154738-chapters)

<a name="work-7707287096683154738-chapter-5"></a>

### 00:05:45　让任务能修正，也能结束

- 课堂用写代码、运行检查、读取错误、返回修订说明反馈。配合一份全局计划，把实现、补测试等环节与总体目标对齐。
- 小步修正时记下做了什么、看到什么结果；重复失败需要停止或交人接手。通过检查后再推进下一步。

**练习**　给一份本地表格故意漏掉必需列，写出检查条件，再试一次修正。为失败和通过各画出下一步。

**自查**　日志能指出错误在哪一步出现，修复后同一检查能通过，循环有明确终点。

<a name="work-7707287096683154738-chapter-6"></a>

### 00:06:53　从一次任务记录找出掉链的环节

- 查看一次请求的经过，区分模型调用、工具调用、注入的资料、失败重试与耗时。片中还提醒，性能评测语境里的 harness 可以指评测框架。
- 原课行程题同时给出预算、老人可接受的步行量和航班时段。先查航班与酒店，再比较总价和到景点的距离；便宜却要走很远的酒店换成备选。交出三套方案让人选，付款和提交身份信息前停下确认。三套都超预算就报告限制。

**练习**　给自己的行程模拟一次班次变动。记录哪段信息失效、如何重新比较、哪里应当暂停等你确认。

**自查**　能从记录重建改动原因，确认前不会出现已购票或已提交资料的状态。

[返回章节目录](#work-7707287096683154738-chapters)

<a name="work-7707287096683154738-chapter-7"></a>

### 00:08:55　用插件式框架的例子理解复用成本

- 课件讨论 DeepSeek Harness，把模型适配、工具与外层流程分开。替换一部分时，仍需观察同一任务在不同模型或插件下的结果。
- 插件越多，描述、工具和规则越占输入空间。共享状态时还要考虑兼容、权限、可回滚与可复现。把这些写成验收项。

**练习**　画一个最小系统，只留一项查询工具。再假设加一个插件，列出新的权限、上下文占用和恢复手段。

**自查**　能为新增插件给出一个能测试的收益，并能指出停用后原流程能否继续。

[返回章节目录](#work-7707287096683154738-chapters)

<a name="work-7707287096683154738-chapter-8"></a>

### 00:10:55　决定什么时候值得做完整的 Agent

- 结尾让团队先看业务。固定步骤适合清楚的工作流，查材料回答的问题可以先试检索；确实需要根据反馈选择下一步时，再投入循环、工具和观测。
- 把全局与单项目的规则分开管理，让它们各有适当的上下文空间。判断价值时用自己的任务结果验证。
- 讲者最后给出实际衡量办法。用同一组任务跑两遍，记成功多少次、人工接管多少次、每次耗时和成本。改过规则后重跑旧任务，查看有没有破坏原先通过的结果。

**练习**　把三件常做的事分别放入「固定流程」「资料问答」「需要动态执行」三栏，选成本最小的一件做试验。

**自查**　从目标、材料和执行回报三方面解释选择。即使只用最简单的方案，也能说清它怎样交付并验收。

## 设计能完成任务的 Agent：从行动边界到规划、工具与记忆

<a name="work-7694528981122551066"></a>

**学习场景**　给一个普通业务助手画出可执行的工作流，先在纸上用一项低风险任务测试。

- 沿用一项任务贯穿课堂。明确哪些动作交给系统，在流程中分别安放规划、工具、记忆、确认和停止条件。
- 每章的「练习」和「自查」由本库按原作设计。按章节顺序做完后，保留自己的结果供比较。

### 00:00:00　把一句请求翻译成可检查的交付

- 开头先给了入门学习路线，随后用「查不到直飞航班怎么办」引出主体。把系统画成能查资料、做计划、调工具并依据结果修正的助手；写下用户真正要拿到的结果。
- 写清楚这次结束时应当看到什么，以及哪些资料算完成的证据。比如一份会议摘要要有决定、负责人和未决项。

**练习**　用自己的会议记录作输入，写下预期交付物，再单列资料里没有、暂时不能确定的字段。

**自查**　把结果给同事看，对方能逐项指出已完成和需追问的地方。

[返回章节目录](#work-7694528981122551066-chapters)

<a name="work-7694528981122551066-chapter-2"></a>

### 00:02:23　按后果划定可以自行决定的范围

- 把动作按风险和复杂度分开。只读、可撤回的整理可以直接推进；涉及替人承诺、付费或外发时，单列确认点。
- 确认请求应告诉人要做什么、依据是什么、会影响谁。常规动作不必反复询问。

**练习**　给任务分三个动作：读记录、生成草稿、发给全组。分别写谁可以决定，在哪一步停下。

**自查**　即使用户只说「处理好」，流程也能先做出草稿，并在发送前停住。

[返回章节目录](#work-7694528981122551066-chapters)

<a name="work-7694528981122551066-chapter-3"></a>

### 00:03:41　在固定流程和探索式规划之间选择

- 作者把两种规划比作汉堡流水线和侦探查案。固定步骤按顺序完成；信息不齐的部分则先找线索，用新证据决定下一步。一个任务中可以混用：先按固定清单核对必需信息，再探索候选方案。
- 给每步写出进入条件和结束条件。未知项需要的是下一条证据，盲目多走几步不会让结论更可靠。

**练习**　把「汇总固定表格」和「解释两份记录为何矛盾」各画成一张流程图。为后者加一个根据新证据分叉的位置。

**自查**　流水线每步都有明确的下游输入；探索路线遇到证据不足能提出具体问题。

[返回章节目录](#work-7694528981122551066-chapters)

<a name="work-7694528981122551066-chapter-4"></a>

### 00:05:00　把计划接到有明确输入输出的工具

- 调用前检查前提条件和参数格式，列出主工具与备选。把「未查到」「接口超时」「查到多个选择」写成不同的结果，决定何时重试、换来源或请人补条件。
- 课中遇到原定选项暂停办理时，会先查同类备选并比较差异。练习回到开头的旅行问题：查不到直飞，先列一份可选中转和新增耗时；涉及放宽用户条件，要把差异交给用户决定。

**练习**　模拟三次查航班：直飞有票、直飞为空、有中转但超过用户允许的总时长。逐次写出输入、返回值、下一步动作和要给用户看的信息。

**自查**　三份记录分别走到展示直飞、展示合规备选、询问是否放宽时长。没有一次把「查不到直飞」误当成「没有办法抵达」。

### 00:06:56　决定什么只记一会儿、什么值得长期保存

- 把当前任务所需的材料放进短期上下文，把未来还会影响选择的稳定事实或偏好另存。长期记忆要允许更正。
- 在开始规划时先取出相关的长期偏好。课中用熟客进门前就记得其饮食偏好的例子说明顺序。旧记录和近期反复提出的要求冲突时，注明时间，核实后再更新。

**练习**　把「本周会议改在周五」和「团队长期使用同一份纪要模板」分开保存，再模拟下个月的新会议。

**自查**　下次可复用模板；临时的周五变更不会变成永久日程。

### 00:08:46　让人能接手，也让系统会停

- 把查询阶段、目前拿到的结果和还缺什么显示给用户。为同一问题规定最大步数或重试次数，记录每次是否得到新信息；达到上限就停止重复调用。

- 让电脑与自己的 Pi 使用同一局域网。在电脑终端运行 ssh user@microduck.local，主机名无法解析时把 microduck.local 换为查到的板子 IP。输入上一步设定的口令。进入项目目录 cd ~/microduck，再运行 PYTHONPATH=src .venv/bin/python src/main.py。
- 先扶住机身，等舵机上力回到中立姿态。在平整地面上按 v 开启步态，轻点方向键观察前进或转向；按 x 把速度归零，按 v 停走，按 q 退出。首次通电身体严重偏向一侧时，先退出查左右 ID、舵盘中位和 IMU 方向。
- 结束后在 Pi 上按工程说明关机，等系统关机再断开电池。片尾展示了实机行走效果和制作中仍可改进之处。

**练习**　按「连接 → 回中 → 走出一小步 → 停止 → 关机」完成一次验收。逐项记下是在哪一步首次出现异常。

**自查**　机身在回中时姿态合理，指令和移动方向对应，操作者能让它立即停下并正常退出。若无法回中，先回到编号和接线两章。

## 判断多条网络线路能否为下载提速

**学习场景**　有 Wi-Fi、手机热点等多条接入线路，想知道聚合是否对自己的任务有效时。

- 先看任务会不会发起多个连接。原片演示的 net-merge 用虚拟网卡把不同连接分派给不同线路，单个连接始终走一条线。

- 检查是否实际上共用一条上游宽带，以及是否有 VPN 占用虚拟网卡。单线程下载也不能按片中的方式叠加带宽。
